# Инструкции AI-инструментам разработки Personal-AI-Agent

Эти инструкции относятся к работе над репозиторием. Они не являются реализацией
поддержки AGENTS.md или SKILL.md в разрабатываемом агенте.

## README.md

Не добавляй, не удаляй и не изменяй содержимое корневого `README.md` без прямой
просьбы пользователя изменить именно этот файл. Общая задача по разработке,
подготовке проекта или обновлению документации такой просьбой не считается.

## До изменений

1. Полностью изучи `docs/ARCHITECTURE.md` — основной источник требований.
   Изучи также `docs/CONTRACTS.md`, README и инструкции в затрагиваемых каталогах.
2. Проверь текущую ветку, `git status`, remote и существующие файлы. Не теряй
   пользовательские изменения при переключениях. Работай только внутри этого проекта.
3. При противоречиях сначала сообщи о проблеме. Предложи минимальное совместимое
   решение; существенные архитектурные решения самостоятельно не принимай.
   Не редактируй `docs/ARCHITECTURE.md` без явного разрешения.

## Реализация

4. Соблюдай структуру `src/ai_agent/`, согласованный стек и распределение
   ответственности из архитектуры. Собственный Agent Loop относится только к Core.
   Не используй готовые агентные фреймворки вместо его реализации.
5. Не изменяй `shared/` без явного согласования. Разрешение на первоначальное
   создание общей основы распространяется на её подготовку в текущей задаче;
   дальнейшие изменения контрактов согласовываются отдельно.
6. Не меняй чужие модули без необходимости и разрешения владельца. Компоненты
   связывай через общие контракты; не импортируй внутренние классы в обход них.
7. Не создавай циклические зависимости. `shared/` не должен зависеть от
   реализаций Core, инфраструктуры, памяти или интерфейсов.
8. Используй type hints и async/await для согласованных асинхронных интерфейсов.
   Новые зависимости добавляй только по необходимости и обновляй uv.lock.
9. Пиши тесты новой функциональности и ошибок, запускай подходящие проверки
   после изменений. Базовые команды: `uv run --locked pytest`, `uv build`.
   Не заявляй об успешных проверках, которые не запускались.
10. Не выдавай заглушки за работающие компоненты. Черновые контракты не считай
    окончательно утверждёнными без подтверждения. Сохраняй их статус в документации.

## Безопасность и Git

11. Не добавляй ключи, пароли, токены и реальные локальные данные в репозиторий
    или логи. Используй `.env.example` без секретов.
12. Без явного разрешения пользователя не выполняй git commit, push, merge,
    rebase, reset --hard, clean, force push, удаление веток и изменение истории.
    Не меняй глобальные настройки Git ради работы с этим репозиторием.
13. `main` — стабильная ветка, `develop` — интеграционная, `feature/...` —
    разработка компонентов через PR в develop. В первоначальной подготовке
    работай только в локальной develop; feature-ветки не создавай.

## Отчётность

14. Выполняй задачи небольшими логически завершёнными этапами. После каждого
    этапа сообщай результат, проверки и предлагай название коммита, не создавая его.
15. В итоговом отчёте укажи изменённые файлы, результат тестов, активную ветку,
    нерешённые вопросы и действия для команды. Документация должна отражать
    реальное состояние проекта, а не планы как готовую функциональность.
