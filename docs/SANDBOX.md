# Локальный пробный запуск

Это демонстрационный запуск: Core и файловые инструменты работают внутри
контейнера, а вызовы моделей идут через отдельный LiteLLM Proxy к OpenAI.
История, пересказы и счётчики одного демо-диалога хранятся в локальном PostgreSQL.
Очередь, долговременная память с векторным поиском, политики бюджетов и
полноценная наблюдаемость отсутствуют.

## Вход и запуск

Нужны Docker Desktop с Docker Compose и доступ к OpenAI. Запусти `./damir login`:
LiteLLM покажет ссылку и код, который нужно ввести на странице OpenAI. В настройках
безопасности аккаунта должен быть разрешён вход по коду устройства. Вход хранится
в отдельном Docker-томе `damir_auth`; токены обновляет LiteLLM. Существующие
учётные данные Codex не используются. Повторная команда использует текущую сессию.

После входа запусти `./damir` (или `./damir run`). Команда запускает шлюз и консоль агента;
`/help` показывает команды, `/models` — настроенные модели, `/tokens` — расход токенов диалога,
`/context` — оценка текущего контекста, `/compress` вручную сжимает
историю, `/exit` завершает консоль. Доступность моделей
зависит от аккаунта. Ключ между агентом и шлюзом создаётся локально в
игнорируемом `.uv-cache/`; API-ключ OpenAI не нужен. Доступ к папке проекта,
Docker и Docker-томам следует ограничить владельцем компьютера.
В меню моделей `0` (или `/exit`) возвращает в чат без смены модели. Список
берётся из `config/litellm.yaml`, а не из каталога конкретного аккаунта: модель
может отображаться в списке, но быть недоступной для подписки.
Неизвестные команды, начинающиеся с `/`, не передаются модели.

Для команды `damir` из любой папки на macOS/Linux один раз установи ссылку:

```sh
./install-damir
```

Скрипт создаёт ссылку в `~/.local/bin`, не перезаписывая существующий файл. Если
этой папки нет в PATH, добавь её в настройки своей оболочки. Затем перейди в папку
проекта и запусти агента:

```sh
cd "/путь/к/Todo List"
damir
```

Текущий каталог подключается в оба контейнера как `/workspace` с правом записи.
Дамир может читать и изменять файлы в нём и читать `AGENTS.md`; выбирай каталог
осознанно. По умолчанию каждой папке соответствует своя история: идентификатор
зависит от её полного пути, поэтому после переименования или переноса будет создана
новая история. При запуске из каталога Personal-AI-Agent сохраняется прежнее
поведение: используется его `workspace` и прежний локальный диалог. При явно
заданном `DAMIR_SESSION_ID` используется указанный идентификатор. Если переместить
сам репозиторий Дамира, ссылку потребуется установить заново.

На Windows можно добавить каталог Personal-AI-Agent в пользовательский PATH, затем
перейти в проект и запустить `damir`. Для временного PATH в PowerShell из каталога
Personal-AI-Agent выполни `$env:PATH += ";$PWD"`. Требуется PowerShell 7.
Проверка на реальной Windows пока необходима.

Консоль передаёт модели системный промпт с характером Дамира: уверенный,
язвительный помощник, который остаётся полезным и бережным в серьёзных ситуациях.
Промпт добавляется в каждый запрос к модели и не записывается в историю диалога.
Вместе с ним передаются дата, время и часовой пояс на начало хода. Они сохраняются
неизменными при вызовах инструментов в рамках одного хода.
Команда `damir` пытается определить часовой пояс компьютера; если это не удалось,
она сообщает о переходе на UTC. Пояс можно задать явно, например:
`DAMIR_TIMEZONE=Asia/Tomsk ./damir run`. Указывается имя часового пояса из базы
IANA. Время может устареть во время выполнения хода и обновится при следующем.

Перед каждым запросом LiteLLM оценивает число входных токенов выбранной модели,
включая инструменты; ядро добавляет запас к оценке. Эта оценка не равна точному
подсчёту провайдера. Рабочий бюджет по умолчанию — 30 000 токенов; его можно
задать через `DAMIR_CONTEXT_TOKENS=40000 ./damir run` (минимум 4096).
Бюджет также ограничивается сведениями шлюза о модели, оставляя запас, и сверху
ограничен 128 000; при неизвестном лимите — 64 000. Сведения о модели могут
относиться к API и отличаться от лимитов подписки ChatGPT, поэтому гарантий
помещения в окно модели нет. Генерация использует Responses API через шлюз;
выходные элементы, включая служебные элементы reasoning при их наличии,
сохраняются в истории диалога и передаются обратно той же модели. Старые диалоги
без них остаются совместимыми с новой версией. Старые версии приложения не смогут
прочитать новые записи с этим полем без миграции.
Время обновляется между ходами, а сжатие меняет историю: при изменении префикса
провайдер может не использовать ранее переданное reasoning-состояние.
Счётчик шлюза работает с форматом сообщений; адаптер включает в оценку
зашифрованные reasoning-элементы как текст. Оценка может отличаться от реального
числа токенов, занятых состоянием модели.

При превышении бюджета старые ходы пересказываются через шлюз; особо длинные ходы
обрабатываются частями. Системные и проектные инструкции и текущий ход остаются
целыми. `/compress` включает использование пересказа вручную и для следующих
запросов, даже если автоматический порог ещё не достигнут. Пересказы кешируются
в PostgreSQL по содержимому и повторно используются при совпадении. Исходная
история не удаляется. Если пересказ не уменьшил оценку контекста, `/compress`
сообщит об этом. Суммаризация расходует дополнительные запросы и может
упускать детали; если текущий ход слишком велик или пересказ не удался, агент
вернёт ошибку. При отсутствии счётчика подсистема Core использует байтовую оценку;
демонстрационная консоль требует работающий счётчик шлюза.

Команда `/tokens` показывает суммарное число токенов диалога по данным шлюза,
включая предыдущие запуски, входные и выходные токены. В сумму
входят также запросы на сжатие. Если шлюз не вернул полные сведения, консоль
выводит знак ≥: итог тогда может быть неполным. Это не счётчик
использования всей подписки. Команда `/context` запрашивает оценку сохранённого
контекста, включая системные и проектные инструкции и схемы инструментов; текст
следующего сообщения в неё не входит. Если готовый пересказ подходит, он учитывается
вместо старой истории; новые сообщения добавляются к нему. Команда не вызывает
генерацию нового пересказа и сообщает об ошибке, если оценить контекст не удалось.
Процент относится к рабочему бюджету, а не к точному окну модели; метаданные
шлюза могут не совпадать с окном модели для подписки ChatGPT.

PostgreSQL запускается в отдельном контейнере без публикации порта на хост.
Данные диалога, включая запросы, ответы и результаты инструментов, хранятся в
локальном Docker-томе `damir_postgres` до его удаления. Пароль базы создаётся в
игнорируемом `.uv-cache/damir-db-password`: сохраните его вместе с томом для
восстановления. Это временный демонстрационный адаптер `IContextStore`, не общая
реализация памяти команды. Он блокирует одновременное открытие одной сессии в
двух экземплярах демо-консоли; общая очередь и межканальная синхронизация не готовы.

## Границы и ограничения

Агент работает под непривилегированным пользователем, с read-only корнем,
временным `/tmp`, без Linux capabilities, с ограничением памяти, CPU и процессов.
Он подключён к внутренней сети с Proxy и PostgreSQL; наружу выходит Proxy.
Docker socket агенту не передаётся. Монтируется предназначенный для тестов
workspace с правом записи. Это контейнерная граница для данного примера, а не
доказательство полной безопасности Docker или защита от всех уязвимостей хоста и
контейнерного движка.
Проверки путей в инструментах отдельно не гарантируют защиту от гонок и жёстких
ссылок.

Инструмент `shell.execute` выполняет команды без подтверждения в отдельном
контейнере `shell-sandbox`, с которым агент общается через Unix-сокет. Для каждого
запуска агента создаются собственные контейнер команд и том сокета; они удаляются
после завершения сеанса. Это позволяет одновременно работать с разными папками.
Контейнер не подключён к сети, не имеет Docker socket или ключей шлюза и базы.
Рабочий каталог — общий `/workspace`, файлы которого команды могут менять и
удалять. Корневая файловая система доступна только для чтения; процессы, память и
CPU ограничены. Контейнер не перезапускается после команд: фоновые процессы и
файлы в `/tmp` могут сохраняться между вызовами до остановки контейнера.
При таймауте или отмене выполняющийся процесс и его дерево останавливаются, но
уже отделившиеся процессы могут продолжать работать. На команду выделено 30 секунд
по умолчанию (от 1 до 120); stdout и stderr ограничены 16 384 символами каждый.

Сейчас поддерживаются `/bin/sh` и PowerShell 7 (`pwsh -NoLogo -NoProfile -Command`)
внутри Linux-контейнера на хостах с Docker. Это Linux-версия PowerShell, а не
нативная оболочка Windows или macOS: доступ к ОС хоста не предоставляется.
Нативные средства Windows и macOS требуют отдельной реализации и проверки.
Контейнер не является абсолютной защитой от уязвимостей контейнерного движка; workspace остаётся доступен для записи.

### Запуск на Windows

Для запуска подготовлены `damir.cmd` и `damir.ps1`: требуются PowerShell 7+
(`pwsh`) и Docker Desktop в режиме Linux-контейнеров. Из папки проекта:

```powershell
.\damir.cmd login
.\damir.cmd run
```

Эквивалентно можно вызвать `pwsh -NoProfile -File .\damir.ps1 login` и затем
`pwsh -NoProfile -File .\damir.ps1 run`. Скрипт создаёт локальные ключи в
игнорируемой папке `.uv-cache`. Для PowerShell 7.0–7.1 автоматическое
преобразование часового пояса Windows в IANA может быть недоступно: скрипт
предупредит и выберет UTC; нужный пояс можно передать в `DAMIR_TIMEZONE`.

Проверка PowerShell-скрипта без реального Docker и без входа в аккаунт:
`pwsh -NoProfile -File .\tests\windows-launcher-check.ps1`. Реальный запуск
Windows и запись файлов через Docker Desktop необходимо проверить на машине с
Windows; подготовленные скрипты пока не являются подтверждением такой проверки.
Для такой проверки сначала убедитесь, что `docker info --format '{{.OSType}}'`
выводит `linux`, затем выполните проверку скрипта, `login` и `run`. В диалоге
попросите Дамира выполнить `uname -s` и `pwsh -Version`;
ожидаются `Linux` и версия PowerShell 7 или выше. Также попросите создать и
прочитать новый тестовый файл в `workspace` и проверьте его на Windows-хосте.
Коды входа и токены в чат или журнал проверки передавать не нужно.

Образ LiteLLM зафиксирован по digest проверенной локальной версии; обновления
образа и проверка его совместимости выполняются отдельно. Proxy в этом примере не
публикует порт на хост, а его конфигурация не включает базу учёта расходов,
бюджеты или телеметрию. Тесты адаптера используют поддельные HTTP-ответы;
успешная сборка не подтверждает доступность OpenAI или корректность ключа.

## Состояние интеграции

Вход по коду и маршрутизация через провайдер LiteLLM `chatgpt/` подготовлены как
экспериментальный путь. Для подтверждения работы необходима проверка реального
входа, ответа модели и вызова инструмента. ChatGPT backend отличается от обычного
OpenAI API; список моделей и доступность зависят от аккаунта. Учёт денежных
расходов и бюджеты для подписки в этом примере не настроены.

Справка: https://docs.litellm.ai/docs/providers/chatgpt.
