# AI Agent — архитектура проекта и правила командной разработки

**Версия:** 1.0  
**Язык:** C# / .NET 10
**Цель:** разработать персонального AI-ассистента с собственным агентным циклом, инструментами, памятью, несколькими интерфейсами и подключаемыми интеграциями.

## 1. Общая концепция

Разрабатываем одного AI-агента с единой системой выполнения задач.

Агент состоит из независимых компонентов:

1. **Core** — ядро агента, управляющее обращениями к LLM и вызовами инструментов.
2. **Gateway** — единая точка доступа к языковым моделям.
3. **Memory** — краткосрочная и долговременная память.
4. **Interfaces** — CLI, Telegram и API.
5. **Tools / Integrations** — внешние возможности агента.
6. **Sandbox** — безопасное исполнение команд.
7. **Observability** — логирование, трассировка и учёт расходов.

Все компоненты интегрируются через согласованные C#-интерфейсы и модели данных.

**Запрещается реализовывать собственные независимые агентные циклы внутри Telegram-бота, интеграций, памяти или других модулей.**

Только Core управляет Agent Loop.

## 3. Распределение ответственности

### Участник 1 — Core (ядро)

Отвечает за:

- Agent Loop;
- единый реестр инструментов (Tool Registry);
- выполнение вызовов инструментов;
- файловые операции;
- обработку AGENTS.md;
- загрузку SKILL.md;
- подключение MCP-клиентов;
- управление контекстным окном;
- compaction истории;
- обработку ошибок агентного цикла;
- ограничения количества итераций.

Также реализует временные адаптеры к LLM и хранилищу истории для раннего тестирования.

**Не отвечает за:** развёртывание LLM Gateway, полноценную БД памяти, Telegram, инфраструктуру Docker.

### Участник 2 — Infrastructure

Отвечает за:

- развёртывание LiteLLM Proxy;
- конфигурацию моделей;
- учёт токенов и бюджетов;
- Docker-песочницу;
- безопасный запуск команд;
- поддержку PowerShell и Linux shell;
- структурированное логирование;
- OpenTelemetry;
- Langfuse;
- общую инфраструктуру Docker Compose.

Предоставляет ядру реализации интерфейсов LLMClient и SandboxExecutor.

### Участник 3 — Memory & Interfaces

Отвечает за:

- PostgreSQL;
- краткосрочную историю диалогов;
- долговременную память;
- pgvector;
- поиск по сохранённой памяти;
- CLI;
- Telegram-бота;
- общий API backend;
- Redis и очередь задач;
- сохранение статусов выполнения задач.

Предоставляет ядру реализацию интерфейса ContextStore и сервис долговременной памяти.

### Участник 4 — Integrations

Отвечает за:

- интернет-поиск;
- напоминания по расписанию;
- Google Calendar;
- интеграцию с внешним календарём;
- GitHub;
- дополнительные инструменты, если останется время.

Все интеграции реализуются через единый интерфейс Tool.

**Интеграции не вызывают LLM напрямую и не управляют Agent Loop.**

## 5. Основные контракты

Контракты реализуются через C#-интерфейсы, модели данных и асинхронные методы. Актуальные сигнатуры находятся в `src/ai_agent/shared/` и `docs/CONTRACTS.md`. Примеры ниже показывают сигнатуры C#; полные определения находятся в исходном коде.

Ниже описаны согласуемые интерфейсы. Точные классы и поля фиксируем в `shared/` до начала интеграции компонентов.

### 5.1. LLMClient

Ядро должно иметь возможность вызвать LLM независимо от конкретного провайдера.

```csharp
public interface ILlmClient
{
    Task<LlmResponse> CompleteAsync(IReadOnlyList<Message> messages, IReadOnlyList<ToolDefinition> tools, CancellationToken cancellationToken = default);
}
```

LLMResponse содержит:

- `content` — текст ответа;
- `tool_calls` — список вызовов инструментов;
- `finish_reason` — причина завершения;
- `usage` — сведения о токенах.

Каждый вызов инструмента содержит:

- `id` — уникальный ID вызова;
- `name` — название инструмента;
- `arguments` — аргументы.

Core не должен зависеть от формата ответов конкретного LLM API.

### 5.2. Tool

Каждый инструмент должен реализовывать единый контракт.

```csharp
public interface ITool
{
    string Name { get; }
    string Description { get; }
    IReadOnlyDictionary<string, JsonElement> Parameters { get; }
    Task<ToolResult> ExecuteAsync(IReadOnlyDictionary<string, JsonElement> arguments, CancellationToken cancellationToken = default);
}
```

`parameters` описывает аргументы инструмента в формате JSON Schema.

Результат ToolResult содержит:

```csharp
public sealed class ToolResult
{
    public required bool Success { get; init; }
    public required string Content { get; init; }
    public string? Error { get; init; }
}
```

Вызовы инструментов проходят через Tool Registry.

Ядро отвечает за проверку аргументов, выбор инструмента, обработку результата и передачу его обратно LLM.

Один ответ модели может содержать несколько вызовов инструментов.

### 5.3. ContextStore

Контракт хранилища истории:

```csharp
public interface IContextStore
{
    Task<IReadOnlyList<Message>> GetMessagesAsync(string sessionId, CancellationToken cancellationToken = default);
    Task AppendMessageAsync(string sessionId, Message message, CancellationToken cancellationToken = default);
    Task ReplaceMessagesAsync(string sessionId, IReadOnlyList<Message> messages, CancellationToken cancellationToken = default);
}
```

Core реализует алгоритм управления контекстом и compaction.

Memory реализует постоянное хранение истории.

Для MVP все сообщения используют роли:

- system;
- user;
- assistant;
- tool.

Сообщения с вызовами инструментов должны сохранять их ID, названия и аргументы. Ответы инструментов должны ссылаться на соответствующий ID вызова.

### 5.4. SandboxExecutor

```csharp
public interface ISandboxExecutor
{
    Task<CommandResult> ExecuteAsync(string command, string workspace, int timeout = 30, CancellationToken cancellationToken = default);
}
```

CommandResult содержит:

- `exit_code`;
- `stdout`;
- `stderr`;
- `timed_out`.

Запуск команд осуществляется через SandboxExecutor.

Core не запускает произвольные команды ОС напрямую.

Все команды выполняются с ограничением времени, рабочего каталога, доступных ресурсов и прав.

Опасные операции требуют отдельного подтверждения или отклоняются политикой безопасности.

### 5.5. Agent

Единая точка запуска агента:

```csharp
public interface IAgent
{
    Task<AgentResult> RunAsync(string sessionId, string userMessage, CancellationToken cancellationToken = default);
}
```

AgentResult содержит:

- `session_id`;
- `response`;
- `status`;
- `error`, если выполнение завершилось ошибкой.

Новые интерфейсы пользователя должны обращаться к этому методу через сервис выполнения задач, а не реализовывать собственную агентную логику.

Асинхронные операции принимают необязательный `CancellationToken` и должны
кооперативно реагировать на отмену. Запрошенная отмена Agent.run возвращает
статус CANCELLED. Передача токена сама по себе не гарантирует остановку
операции, если реализация его игнорирует. Правила восстановления частично
записанной истории и отмены процессов песочницы согласуются отдельно.

## 6. Правила Agent Loop

Выполнение запроса происходит по следующему сценарию:

1. Получаем пользовательский запрос.
2. Загружаем историю диалога.
3. Загружаем необходимые инструкции и контекст.
4. Проверяем бюджет контекстного окна.
5. При необходимости выполняем compaction.
6. Отправляем сообщения и доступные инструменты в LLM.
7. Если модель запросила инструменты, выполняем их.
8. Возвращаем результаты инструментов в историю.
9. Повторяем цикл.
10. Если модель завершила ответ без вызовов инструментов, возвращаем результат пользователю.

Необходимо предусмотреть:

- лимит итераций Agent Loop;
- таймауты инструментов;
- обработку недоступности LLM;
- обработку неизвестных инструментов;
- обработку неверных аргументов;
- ограничение параллельных операций;
- отмену задачи;
- сохранение истории;
- корректное завершение.

По умолчанию для первой реализации используем максимум 20 итераций Agent Loop с возможностью настройки.

## 7. Правила подключения инструментов

У каждого инструмента должно быть уникальное имя.

Примеры:

```text
filesystem.read_file
filesystem.write_file
filesystem.edit_file

shell.execute

web.search

github.list_repositories
github.create_issue

calendar.list_events
calendar.create_event

reminders.create
```

Название инструмента не должно меняться без согласования.

Инструмент обязан:

- иметь описание своего назначения;
- описывать параметры через JSON Schema;
- проверять входные данные;
- возвращать ToolResult;
- обрабатывать ошибки;
- не зависеть от интерфейса пользователя;
- не хранить собственную историю диалога.

Каждая интеграция регистрируется в Tool Registry.

## 8. Правила взаимодействия интерфейсов

Все интерфейсы используют единый backend.

Telegram не должен содержать собственного Agent Loop.

CLI не должен создавать независимую систему памяти.

Общая схема:

```text
CLI / Telegram
      |
      v
   API backend
      |
      v
 Task Service
      |
      v
 Redis Queue
      |
      v
 Agent Worker
      |
      v
     Core
```

Для выполнения задачи используется `task_id`.

Минимальные состояния:

```text
PENDING
RUNNING
COMPLETED
FAILED
CANCELLED
```

История диалогов хранится по `session_id`.

Задачи выполняются по `task_id`.

**Важно:** одна сессия должна иметь единый порядок изменения истории. Одновременное выполнение нескольких задач одной сессии нужно сериализовать или контролировать блокировкой.

Два интерфейса используют общую память и очередь задач.

Для тестирования Core допускается прямой запуск без очереди.

## 9. Работа с памятью

Разделяем три понятия:

**История диалога:** сообщения пользователя, ответы модели, вызовы инструментов и их результаты.

**Контекст LLM:** часть истории и дополнительных инструкций, отправляемая модели в текущем запросе.

**Долговременная память:** сохранённые знания и предпочтения, которые могут использоваться в будущих диалогах.

Compaction относится к Core.

Хранение сообщений и долговременных записей относится к Memory.

Подготовка контекста может использовать долговременную память через отдельный сервис поиска.

Не загружаем всю долговременную память в каждый запрос.

## 10. AGENTS.md и SKILL.md

Core реализует чтение инструкций проекта.

**AGENTS.md:**

- содержит инструкции для агента;
- ищется с учётом иерархии каталогов;
- инструкции применяются к соответствующим областям проекта;
- содержимое не считается системными инструкциями более высокого приоритета.

**SKILL.md:**

- описывает отдельный навык;
- может содержать инструкции и ссылки на дополнительные ресурсы;
- загружается по необходимости;
- не должен автоматически перегружать контекст.

Формат навыков и правила поиска фиксируются отдельно в документации Core.

## 11. MCP

MCP реализуется на стороне Core как адаптер внешних инструментов.

Необходимо поддержать:

- подключение MCP-сервера;
- получение списка доступных tools;
- преобразование описаний в формат Tool Registry;
- вызов MCP-инструмента;
- обработку ошибок подключения и выполнения.

Для первой версии поддерживаем локальные MCP-серверы через stdio.

Поддержку удалённых серверов добавляем после рабочего MVP.

## 13. Правила Git

Используем единый репозиторий.

Основные ветки:

- `main` — стабильная версия;
- `develop` — объединение готового функционала;
- `feature/...` — разработка отдельных компонентов.

Примеры:

```text
feature/agent-core
feature/llm-gateway
feature/memory
feature/telegram
feature/github-integration
```

Непосредственные изменения в `main` запрещены.

Интеграция выполняется через Pull Request.

Перед объединением:

1. Проект запускается.
2. Тесты проходят.
3. Изменения не нарушают общие контракты.
4. Новая функциональность описана в README или документации.
5. Изменения в `shared/` согласованы.

## 14. Правила разработки

1. Не используем готовые агентные фреймворки вместо собственного Agent Loop.
2. Все внешние операции выполняются асинхронно там, где это применимо.
3. Компоненты взаимодействуют через согласованные интерфейсы.
4. Не создаём циклических зависимостей между модулями.
5. Не импортируем внутренние классы чужих модулей в обход публичных контрактов.
6. Используем type hints.
7. Пишем тесты для основных сценариев.
8. Не сохраняем секреты в логах.
9. Все ошибки обрабатываются явно.
10. Не меняем общие модели данных в одиночку.

## 15. Контрольные точки

### Этап 1 — Согласование контрактов

Должны быть готовы:

- структура проекта;
- модели `shared/`;
- интерфейсы `shared/`;
- перечень инструментов;
- контракт Agent;
- контракт задачи и сессии.

После этого каждый участник начинает независимую разработку.

### Этап 2 — Независимые прототипы

Core:

- Agent Loop с mock LLM;
- файловые инструменты.

Infrastructure:

- работающий LLM Gateway;
- прототип SandboxExecutor.

Memory & Interfaces:

- БД и история сообщений;
- CLI;
- прототип Telegram.

Integrations:

- минимум два инструмента;
- тесты их выполнения.

### Этап 3 — Первая интеграция

Проверяем полный сценарий:

1. Пользователь отправляет запрос через CLI.
2. Запрос попадает в Core.
3. Core обращается к LLM Gateway.
4. LLM выбирает инструмент.
5. Инструмент выполняется.
6. Результат возвращается модели.
7. История сохраняется в PostgreSQL.
8. Ответ возвращается пользователю.

### Этап 4 — Полная интеграция

Подключаем:

- Telegram;
- общую очередь;
- долговременную память;
- MCP;
- Docker-песочницу;
- наблюдаемость;
- оставшиеся интеграции.

### Этап 5 — Тестирование и защита

Проверяем:

- работу всех компонентов;
- работу через два интерфейса;
- сохранение общей истории;
- обработку ошибок;
- compaction;
- выполнение инструментов;
- логирование и трассировку;
- восстановление после перезапуска.

## 16. Главный принцип

**Разрабатываем одну систему, а не четыре отдельных приложения.**

Core управляет агентом.

Infrastructure предоставляет инфраструктурные сервисы.

Memory & Interfaces обеспечивает хранение и взаимодействие с пользователем.

Integrations предоставляет инструменты.

Каждый модуль должен подключаться через согласованные контракты без переписывания логики других компонентов.
