## Утверждённые интерфейсы и модели

В `shared/protocols.py` подготовлены пять асинхронных Protocol:

| Контракт | Методы |
| --- | --- |
| `LLMClient` | `complete(messages, tools) -> LLMResponse` |
| `Tool` | `name`, `description`, `parameters`; `execute(arguments) -> ToolResult` |
| `ContextStore` | `get_messages`, `append_message`, `replace_messages` |
| `SandboxExecutor` | `execute(command, workspace, timeout=30) -> CommandResult` |
| `Agent` | `run(session_id, user_message) -> AgentResult` |

Protocol описывает структурный интерфейс, наследование от него не обязательно.
`runtime_checkable` проверяет наличие членов, а не полную корректность типов
и сигнатур. Тесты отдельно сверяют сигнатуры и вызывают async-методы тестовых адаптеров.

Все десять моделей обмена в `shared/models.py` запрещают неизвестные поля
через Pydantic `extra="forbid"`, включая вложенные модели. Произвольные ключи
в словарях arguments и parameters допустимы: это данные инструмента.
Обязательные идентификаторы должны содержать хотя бы один непробельный символ.
Они не генерируются и не обрезаются автоматически.

В `shared/models.py`:

- `ToolDefinition`: `name`, `description`, `parameters` (JSON Schema).
- `ToolCall`: непустой `id`, `name`, `arguments`.
- `Message`: роли `system/user/assistant/tool`, текст `content`, список
  `tool_calls` и ссылка `tool_call_id`. Непустой список tool_calls разрешён
  только assistant. Content может отсутствовать или быть None только у assistant
  с вызовами инструментов; иначе требуется строка. Пустая строка допустима,
  в том числе для ответа инструмента. Для роли `tool` непустая ссылка обязательна.
  Сохранение истории обязано
  сохранять вложенные вызовы без потери ID, имени и аргументов.
- `ToolResult`: ровно `success`, `content`, `error=None`, как в архитектуре.
  При success=True error должен быть None; при success=False требуется непустое
  непробельное объяснение. Content остаётся строкой и может быть пустым при ошибке.
  ID результата передаётся в `Message.tool_call_id`, а не добавляется к ToolResult.
- `LLMResponse`: `content=None`, `tool_calls=[]`, `finish_reason=None`, `usage=None`.
  Причина завершения нормализована: stop, tool_calls, length, error, unknown.
  Если провайдер не прислал значение, используется None. Неизвестное значение
  провайдера Gateway преобразует в unknown. Адаптация — ответственность Gateway.
- `TokenUsage`: input_tokens, output_tokens, total_tokens — необязательные
  неотрицательные целые числа. Строки, bool и дробные значения не принимаются.
  None означает отсутствие данных, 0 — известный ноль. Сумма и стоимость
  автоматически не вычисляются. Сам usage тоже может отсутствовать.
- `CommandResult`: обязательный `exit_code: int | None`, `stdout=""`, `stderr=""`,
  `timed_out=False`. Неизвестный код обозначается None. При таймауте timed_out=True;
  известный код и частичный вывод сохраняются, фиктивный код не вычисляется.
- `AgentResult`: непустой session_id, response=None, обязательный status, error=None.
  Допустимы только COMPLETED, FAILED, CANCELLED; правила приведены ниже.
- `TaskStatus`: `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, `CANCELLED`.
- `Task`: непустые task_id и session_id, обязательный user_message,
  status=PENDING, result: AgentResult | None = None.
- `Session`: только непустой session_id; идентификатор создаёт общий backend.

### Статусы результата агента и задачи

| AgentResult.status | Требование |
| --- | --- |
| COMPLETED | Непустой непробельный response; error должен быть None |
| FAILED | Непустой непробельный error; response необязателен, частичный ответ можно сохранить |
| CANCELLED | response и error необязательны; переданный error не может быть пустым |

Лимит итераций означает FAILED с объяснением в error. Статуса limit_reached нет.
Это требование к будущему Core, а не реализованный Agent Loop.

Для Task:

- User_message сохраняется без изменения при создании и JSON-сериализации.
- Для PENDING/RUNNING результат отсутствует.
- Для COMPLETED/FAILED результат обязателен: в нём находится ответ или причина ошибки.
- Для CANCELLED результат необязателен, например при отмене до запуска агента.
- Если result присутствует, его status и session_id должны совпадать с задачей.
- Статусы сериализуются в JSON как указанные строки и восстанавливаются Pydantic.
  Переходы между состояниями здесь не реализованы.

### Исключения и настройки

Ожидаемая ошибка инструмента — `ToolResult(success=False, content="", error="...")`.
Инфраструктурный сбой — исключение на основе AgentError. Автоматических повторов
нет. Конкретные подклассы исключений добавляются при реализации компонентов.

Settings — обычная Pydantic BaseModel с явным from_env(); библиотека
pydantic-settings не используется. Имена переменных соответствуют архитектуре.
Пустые необязательные сервисные значения считаются отсутствующими. Сервисные
настройки могут отсутствовать до запуска соответствующего компонента.
Лимит итераций по умолчанию 20, workspace — ./workspace. Импорт не читает .env,
не создаёт каталоги и не подключается к сервисам.

## Границы компонентов

`shared` зависит только от стандартной библиотеки и Pydantic;
`protocols` импортирует только модели. Зависимостей от Core, провайдеров,
PostgreSQL, Redis, Docker или интерфейсов здесь нет.
Core использует LLMClient, ContextStore и SandboxExecutor; интеграции предоставляют
Tool. CLI и Telegram должны вызывать общий backend и сервис задач; прямой вызов
Agent допустим в тестах Core.

Структурная валидация payload относится к Pydantic. Соответствие результатов
истории вызовов и уникальность ToolCall ID проверяет будущий Core. Уникальность
зарегистрированных инструментов и проверка аргументов по JSON Schema относятся
к будущему Tool Registry. Модели сейчас не выполняют эти проверки.

Сериализация задач одной сессии относится к Task Service / Worker. Блокировка
должна покрывать всё выполнение Agent.run, а не только отдельные записи истории.
Сейчас это требование: механизм блокировки, Redis и worker не реализованы.

## Отложенные вопросы

- Точные JSON Schema, ошибки, ограничения и первоначальный набор инструментов.
- Подробная политика ошибок запуска SandboxExecutor, усечение вывода и отмена.
- Конкретная иерархия инфраструктурных исключений и будущая политика retry.
- Формат конфигурационных файлов и приоритеты источников настроек.
- Механизм блокировки задач, восстановление и обработка сбоев worker.
- Жизненный цикл сессий, принадлежность пользователю и сроки хранения.
- Расширенные счётчики токенов и стоимость.
- Контракт поиска долговременной памяти и описания MCP-инструментов.

Эти вопросы не меняют утверждённые поля и не требуют реализации функциональных
компонентов на этапе общей основы.

## Перечень будущих инструментов

Имена из раздела 7 архитектуры: `filesystem.read_file`,
`filesystem.write_file`, `filesystem.edit_file`, `shell.execute`, `web.search`,
`github.list_repositories`, `github.create_issue`, `calendar.list_events`,
`calendar.create_event`, `reminders.create`.
Это примеры для планирования, а не обязательный полный набор MVP. Инструменты
не реализованы. Точные JSON Schema и ограничения согласуют владельцы компонентов.

## Пока не реализовано

Agent Loop, Tool Registry, MCP, файловые и shell-инструменты, Gateway,
PostgreSQL/pgvector и долговременная память, Redis и очередь, Task Service/Worker,
FastAPI endpoints, CLI, Telegram, Docker и наблюдаемость. Подготовлены только
контракты и каталоги с пояснениями. Тестовые адаптеры находятся исключительно в tests.
