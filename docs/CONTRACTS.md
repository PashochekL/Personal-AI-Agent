# Общие контракты компонентов

Источник требований — [ARCHITECTURE.md](ARCHITECTURE.md). Утверждённые поля и
правила основы перенесены с Python на C#; интеграционные решения по-прежнему
согласуются командой. Реализация находится в `src/ai_agent/shared/`.

Асинхронные интерфейсы: `ILlmClient`, `ITool`, `IContextStore`,
`ISandboxExecutor`, `IAgent`. Они не реализуют внешние сервисы и агентный цикл.
Зависимостей от других компонентов в shared нет.

Модели: `ToolDefinition`, `ToolCall`, `Message`, `ToolResult`, `TokenUsage`,
`LlmResponse`, `CommandResult`, `AgentResult`, `AgentTask`, `Session` и
`TaskStatus`. `AgentTask` назван так, чтобы не конфликтовать с `System.Threading.Tasks.Task`.
JSON использует snake_case и строковые статусы. Для сериализации используйте
`ContractJson`: он запрещает неизвестные поля и проверяет вложенные модели.
Десериализация моделей также автоматически вызывает `Validate`; объекты,
созданные в коде, необходимо проверять `Validate()` до передачи через границу
компонента. Словари аргументов и JSON Schema допускают произвольные ключи.

- Обязательные идентификаторы не могут быть пустыми или состоять из пробелов.
- `Message`: роли system/user/assistant/tool; вызовы возможны только у assistant,
  ответ tool содержит `tool_call_id`. Content может отсутствовать только у
  assistant с вызовами. Начальный Core проверяет связность истории и уникальность ID.
- `ToolResult`: при успехе error отсутствует, при ошибке необходима причина.
- `TokenUsage`: необязательные неотрицательные целые значения; ноль отличается от
  неизвестного значения, сумма не вычисляется. Счётчики имеют диапазон C# `int`.
- `LlmResponse`: finish_reason — stop, tool_calls, length, error, unknown или null.
  Нормализация провайдера относится к Gateway.
- `CommandResult`: exit_code обязателен, но может быть null; при таймауте
  сохраняются известный код и частичный вывод.
- `AgentResult`: только COMPLETED, FAILED, CANCELLED. COMPLETED требует непустой
  ответ без ошибки; FAILED требует причину; CANCELLED допускает отсутствие обоих.
- `AgentTask`: PENDING/RUNNING без результата, COMPLETED/FAILED с результатом,
  CANCELLED с результатом или без него. Session и status результата совпадают с задачей.
- Настройки загружаются явно через `Settings.FromEnvironment`: по умолчанию 20
  итераций и `./workspace`; пустые необязательные значения отсутствуют. Секретные
  поля исключены из стандартной JSON-сериализации настроек. `.env` не читается автоматически.

Ожидаемая ошибка инструмента передаётся в `ToolResult`, инфраструктурные ошибки —
через `AgentError`. Повторы, блокировки сессий, восстановление истории, правила
песочницы и схемы будущих инструментов остаются предметом согласования.

Начальные Agent Loop и Tool Registry реализованы в `src/ai_agent/core/`. Реестр
проверяет аргументы по JSON Schema с помощью JsonSchema.Net. Инструменты вызываются
последовательно. Для тестов используются адаптеры модели и хранилища в `tests/CoreTests/`.

Все асинхронные методы `IAgent`, `ITool`, `ILlmClient`, `IContextStore` и
`ISandboxExecutor` принимают необязательный `CancellationToken`. Core передаёт
его шлюзу, хранилищу и инструментам и возвращает `CANCELLED` при запрошенной
отмене. Реализации должны кооперативно реагировать на токен; его передача не
останавливает операции принудительно. Изменение сигнатур требует обновления
реализаций интерфейсов; постоянное хранилище и исполнитель shell-команд ещё не реализованы.
При отмене во время выполнения или сохранения вызова история может остаться незавершённой;
следующий запуск выявит её и завершится ошибкой. Восстановление не реализовано.
Файловые инструменты `filesystem.read_file`, `filesystem.write_file`,
`filesystem.edit_file` и `filesystem.list_directory` предоставляются отдельно и
регистрируются в Tool Registry явно. Пути задаются относительно существующего
workspace; абсолютные пути, `..` и символьные ссылки отклоняются. Текстовые файлы
ограничены 1 МиБ, обход каталогов — глубиной 5 и 1000 элементами. Проверки путей
не являются песочницей: конкурентная подмена путей и жёсткие ссылки требуют
изоляции на уровне ОС. Инструменты следует использовать только в изолированном
workspace. Для демонстрационного запуска Core и файловых инструментов подготовлен
контейнер с отдельным workspace, ограничением ресурсов и отключённой прямой сетью;
это не реализация ISandboxExecutor для будущих shell-команд.

Начальная поддержка инструкций и навыков включается передачей `Workspace` в
конструктор `Agent`. Корневой `AGENTS.md` и метаданные навыков передаются модели
как проектный контекст, не как системные инструкции. Перед файловой операцией
Core находит `AGENTS.md` от корня workspace до каталога цели; при первом
обращении к набору инструкций возвращает его модели и требует повторить вызов.
Инструкции более глубокого каталога идут последними. Поиск выше workspace,
механическое разрешение противоречий и принудительное соблюдение моделью не
реализованы. Инструкции ограничены теми же файловыми проверками, что и инструменты.

Навыки ищутся в непосредственных подкаталогах `workspace/skills/`. `SKILL.md`
должен содержать YAML frontmatter с `name` и `description`; имя совпадает с
именем каталога, допускаются строчные латинские буквы, цифры и одиночные дефисы.
Модель видит метаданные; `skills.load` загружает полный файл по имени, а связанные
ресурсы доступны через файловые инструменты относительно каталога навыка.
`skills.list` показывает каталог. Поддержка экспериментального `allowed-tools`,
исполнение скриптов навыков и автоматическое следование ссылкам не реализованы;
все эти операции остаются под правилами инструментов и песочницы. Ошибочные
навыки приводят к ошибке загрузки каталога, а не игнорируются.

Начальный `LiteLlmClient` обращается к LiteLLM Proxy; пример локальной настройки
OpenAI через proxy и запуска агента находится в `docs/SANDBOX.md`. Пример хранит
историю только в памяти процесса и не заменяет общий backend и очередь. Реальный
шлюз, бюджеты и журналирование необходимо отдельно проверить и настроить.

Таймаут инструментов пока не реализован. Не реализованы compaction, MCP, другие
инструменты, постоянные хранилища, очередь, Task Service/Worker, общий API,
Telegram и наблюдаемость. Запуски одной сессии должен сериализовать будущий Task Service/Worker.
