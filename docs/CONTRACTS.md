# Общие контракты компонентов

Источник требований — [ARCHITECTURE.md](ARCHITECTURE.md). Утверждённые поля и
правила основы перенесены с Python на C#; интеграционные решения по-прежнему
согласуются командой. Реализация находится в `src/ai_agent/shared/`.

Асинхронные интерфейсы: `ILlmClient`, `ITool`, `IContextStore`,
`ISandboxExecutor`, `IAgent`. Они не реализуют внешние сервисы и агентный цикл.
Зависимостей от других компонентов в shared нет.

Модели: `ToolDefinition`, `ToolCall`, `Message`, `ToolResult`, `TokenUsage`,
`LlmResponse`, `CommandResult`, `AgentResult`, `AgentTask`, `Session` и
`TaskStatus`. `AgentTask` назван так, чтобы не конфликтовать с `System.Threading.Tasks.Task`.
JSON использует snake_case и строковые статусы. Для сериализации используйте
`ContractJson`: он запрещает неизвестные поля и проверяет вложенные модели.
Десериализация моделей также автоматически вызывает `Validate`; объекты,
созданные в коде, необходимо проверять `Validate()` до передачи через границу
компонента. Словари аргументов и JSON Schema допускают произвольные ключи.

- Обязательные идентификаторы не могут быть пустыми или состоять из пробелов.
- `Message`: роли system/user/assistant/tool; вызовы возможны только у assistant,
  ответ tool содержит `tool_call_id`. Content может отсутствовать только у
  assistant с вызовами. Необязательный `continuation` содержит непрозрачные
  данные продолжения провайдера и допускается только у assistant. Старые сообщения
  без этого поля совместимы с новой версией. Совместимость односторонняя: старый
  код с запретом неизвестных полей не прочитает записи с `continuation`.
  Начальный Core проверяет связность истории и уникальность ID.
- `ToolResult`: при успехе error отсутствует, при ошибке необходима причина.
- `TokenUsage`: необязательные неотрицательные целые значения; ноль отличается от
  неизвестного значения, сумма не вычисляется. Счётчики имеют диапазон C# `int`.
- `LlmResponse`: finish_reason — stop, tool_calls, length, error, unknown или null.
  Необязательный `continuation` передаёт непрозрачное состояние для записи в
  соответствующее сообщение assistant. Нормализация провайдера относится к Gateway.
- `CommandResult`: exit_code обязателен, но может быть null; при таймауте
  сохраняются известный код и частичный вывод.
- `AgentResult`: только COMPLETED, FAILED, CANCELLED. COMPLETED требует непустой
  ответ без ошибки; FAILED требует причину; CANCELLED допускает отсутствие обоих.
- `AgentTask`: PENDING/RUNNING без результата, COMPLETED/FAILED с результатом,
  CANCELLED с результатом или без него. Session и status результата совпадают с задачей.
- Настройки загружаются явно через `Settings.FromEnvironment`: по умолчанию 20
  итераций и `./workspace`; пустые необязательные значения отсутствуют. Секретные
  поля исключены из стандартной JSON-сериализации настроек. `.env` не читается автоматически.

Ожидаемая ошибка инструмента передаётся в `ToolResult`, инфраструктурные ошибки —
через `AgentError`. Повторы, блокировки сессий, восстановление истории, правила
песочницы и схемы будущих инструментов остаются предметом согласования.

Начальные Agent Loop и Tool Registry реализованы в `src/ai_agent/core/`. Реестр
проверяет аргументы по JSON Schema с помощью JsonSchema.Net. Инструменты вызываются
последовательно. Для тестов используются адаптеры модели и хранилища в `tests/CoreTests/`.

Все асинхронные методы `IAgent`, `ITool`, `ILlmClient`, `IContextStore` и
`ISandboxExecutor` принимают необязательный `CancellationToken`. Core передаёт
его шлюзу, хранилищу и инструментам и возвращает `CANCELLED` при запрошенной
отмене. Реализации должны кооперативно реагировать на токен; его передача не
останавливает операции принудительно. Изменение сигнатур требует обновления
реализаций интерфейсов. Для демо подготовлены локальное хранилище и исполнитель
shell-команд. Общий backend и очередь реализованы в `interfaces/api`;
прямой пример в `examples/SandboxConsole` обращается к Core напрямую.
Обычный `damir` использует HTTP CLI: сессии, модель, ручной навык, расход,
оценка и сжатие контекста обслуживаются backend, как описано в [CLI.md](CLI.md).
HTTP-метаданные задач хранятся в Interfaces без расширения моделей shared.
При отмене или сбое после сохранения вызова инструмента, но до сохранения его
результата, следующий запуск или ручное сжатие дополняет последние незавершённые
вызовы сообщениями о неизвестном результате. Вызовы не повторяются автоматически:
инструмент мог уже изменить внешнее состояние. Существующие результаты сохраняются.
Повреждённая история с незавершённым вызовом в середине отклоняется. Транзакционная
гарантия при неопределённом результате записи хранилища не реализована.
Файловые инструменты `filesystem.read_file`, `filesystem.write_file`,
`filesystem.edit_file` и `filesystem.list_directory` предоставляются отдельно и
регистрируются в Tool Registry явно. Пути задаются относительно существующего
workspace; абсолютные пути, `..` и символьные ссылки отклоняются. Текстовые файлы
ограничены 1 МиБ, обход каталогов — глубиной 5 и 1000 элементами. Проверки путей
не являются песочницей: конкурентная подмена путей и жёсткие ссылки требуют
изоляции на уровне ОС. Инструменты следует использовать только в изолированном
workspace. Для демонстрационного запуска Core и файловых инструментов подготовлен
контейнер с отдельным workspace, ограничением ресурсов и отключённой прямой сетью.
В демонстрационной консоли `shell.execute` без подтверждения вызывает
`ISandboxExecutor`, подключённый к постоянно работающему отдельному Linux-контейнеру
без сети и Docker socket. Доступен общий workspace с правом записи. Контейнер
не перезапускается между командами, поэтому фоновые процессы и временные файлы
могут сохраняться. Реализованы таймаут, отмена и ограничение вывода; доступны
`/bin/sh` и PowerShell 7 для Linux. Нативные команды Windows/macOS не поддержаны.

Начальная поддержка инструкций и навыков включается передачей `Workspace` в
конструктор `Agent`. `.agents/AGENTS.md`, корневой `AGENTS.md` и метаданные навыков передаются модели
как проектный контекст, не как системные инструкции. Перед файловой операцией
Core находит `AGENTS.md` от корня workspace до каталога цели; при первом
обращении к набору инструкций возвращает его модели и требует повторить вызов.
Файл `.agents/AGENTS.md` действует на весь workspace и загружается перед
корневым `AGENTS.md`; вложенные стандартные файлы идут после них.
Инструкции более глубокого каталога идут последними, а модели передаётся правило
их приоритета над родительскими в этой области. Поиск выше workspace,
механическое разрешение противоречий и принудительное соблюдение моделью не
реализованы. Инструкции ограничены теми же файловыми проверками, что и инструменты.

Навыки ищутся в непосредственных подкаталогах `workspace/.agents/skills/` и
прежнего `workspace/skills/`. При совпадении имён выбирается навык из
`.agents/skills/`. `SKILL.md`
должен содержать YAML frontmatter с `name` и `description`; имя совпадает с
именем каталога, допускаются строчные латинские буквы, цифры и одиночные дефисы.
Проверяются типы необязательных полей compatibility, license, metadata и allowed-tools;
их наличие не включает дополнительных разрешений. Модель видит метаданные;
`skills.load` загружает полный файл по имени, а связанные
ресурсы доступны через файловые инструменты относительно каталога навыка.
`skills.list` показывает каталог. Поддержка экспериментального `allowed-tools`,
исполнение скриптов навыков и автоматическое следование ссылкам не реализованы;
все эти операции остаются под правилами инструментов и песочницы. Ошибочные
навыки приводят к ошибке загрузки каталога, а не игнорируются.
Демо-консоль поддерживает `/skill` для просмотра списка и выбора по номеру и
`/skill имя` для выбора по имени: она проверяет файл и явно выбирает навык
для следующего обычного сообщения. `/skill 0` отменяет выбор. Core загружает навык
в проектный контекст текущего хода без зависимости от решения модели вызвать tool;
содержимое не записывается в историю как сообщение пользователя. При следующих
ходах навык заново выбирается вручную или загружается моделью через `skills.load`.
Консоль сообщает имя навыка после его успешной загрузки; просмотр каталога и
ошибочная загрузка не считаются использованием навыка.

Начальный `LiteLlmClient` отправляет генерацию в LiteLLM Proxy через Responses API;
функции и результаты преобразуются из общих контрактов в элементы Responses.
Агент сохраняет выходные элементы, включая reasoning при его наличии, в истории и
повторно отправляет их только для той же настроенной модели и при наличии нужного
зашифрованного состояния. Иначе используются обычные текст и вызовы инструментов.
Старые сообщения без continuation
остаются работоспособны. При сжатии непрозрачные элементы не передаются модели в
тексте пересказа. Счётчик шлюза продолжает принимать `messages`; адаптер добавляет
сериализованные reasoning-элементы для приблизительной оценки выбранной моделью.
Зашифрованное представление и исходное состояние могут токенизироваться по-разному,
поэтому это оценка, а не точный расход. Пример локальной настройки
OpenAI через proxy и запуска агента находится в `docs/SANDBOX.md`. Пример хранит
историю в локальном PostgreSQL и не заменяет общий backend и очередь. Реальный
шлюз, бюджеты и журналирование необходимо отдельно проверить и настроить.

В Core реализована начальная подготовка контекста. Демонстрационная консоль
запрашивает через LiteLLM оценку токенов выбранной модели и задаёт рабочий бюджет;
при отсутствии счётчика Core использует байтовую оценку. Оценка и сведения о лимите
могут отличаться от фактического окна подписки. При превышении бюджета старая
история суммируется через `ILlmClient`, большие ходы могут разбиваться на фрагменты;
активный ход и пары его вызовов/результатов инструментов сохраняются целиком.
Пересказы кэшируются в локальном PostgreSQL, `/compress` включает их ручное
применение. Исходная история не заменяется. Контекст и фактический счётчик токенов
показываются в демонстрационной CLI. Общий backend с очередью описан в
[BACKEND.md](BACKEND.md). Долговременная память
реализована отдельно, как описано ниже.

MCP-инструменты можно зарегистрировать в общем Tool Registry через официальный
.NET SDK; в демонстрационной консоли предусмотрен отдельный контейнер официального
GitHub MCP-сервера в режиме чтения. Этот адаптер также подключён в backend
при включении GitHub через launcher. Список инструментов загружается при запуске;
автоматическое переподключение и обновление списка пока не реализованы. Общий
таймаут произвольных инструментов пока не реализован; для shell есть отдельный
таймаут. Интернет-поиск `web.search` использует отдельный сетевой контейнер и
RSS-выдачу Bing, возвращает заголовки, ссылки и фрагменты; чтение целых страниц
не реализовано. Доступность и релевантность выдачи внешнего сервиса не гарантированы.
Другие внешние интеграции и наблюдаемость пока не реализованы.
Telegram-клиент реализован через HTTP без расширения shared. Персональная
команда `/tg` передаёт текущую сессию CLI в Telegram по одноразовой ссылке;
фактический Telegram ID сохраняется в БД. Поле HTTP-запроса `channel`
(`console` по умолчанию или `telegram`) проверяется при приёме задачи под
блокировкой сессии. Технические ID остаются деталями транспорта.
Возврат по кнопке использует `POST /telegram/{botId}/{lease}/resume`: сервер
проверяет привязанные `user_id`, `session_id` и lease, затем переключает канал
только у свободной сессии. В пределах подтверждённого запуска новая ссылка
при этом не нужна. Новый lease или другая сессия сбрасывает подтверждение:
Telegram не принимает текст и действия до открытия новой ссылки. Поля
`connected` и `workspace_name` описывают активное подключение; название папки
не позволяет изменить настоящий workspace. Меню использует те же операции
`context` и `compress`, выбор модели и навыка хранится в транспортном состоянии.
Инструмент
`filesystem.send_to_telegram` сохраняет снимок файла текущего workspace в очередь
доставки, не вызывает Bot API из Core. В отдельном административном режиме
`damir telegram-isolated` каждому разрешённому ID по-прежнему назначены отдельный
backend, ключ, owner/project и workspace; защищённый `GET /identity`
проверяет назначение до открытия сессии.
См. [TELEGRAM.md](TELEGRAM.md).
Общий ASP.NET Core API,
Task Service и Redis Worker реализованы отдельно; Worker сериализует
выполнение одной сессии через PostgreSQL advisory lock.

Хранение истории вынесено в общий `PostgresContextStore` модуля Memory,
реализующий существующий `IContextStore`. Он также предоставляет операции
сохранения пересказов и предпочтения ручного сжатия; адаптер демонстрационной
консоли связывает их с публичным `IContextSummaryCache` Core. Зависимости
Memory от Core нет. Имена таблиц и формат сообщений сохранены, миграция
существующих диалогов не требуется. API и Worker используют то же хранилище.
Согласованы ASP.NET Core 10 и StackExchange.Redis; HTTP DTO и правила приёма
задач находятся в модуле interfaces/api, без расширения shared. Состояния,
отмена и восстановление описаны в [BACKEND.md](BACKEND.md).

## Долговременная память

Контракты `ILongTermMemory` и `IEmbeddingClient` и модели в `shared/MemoryContracts.cs`
добавлены после явного согласования владельцем проекта. Существующие сигнатуры
`IAgent`, `IContextStore` и `ILlmClient` сохранены.

- `MemoryScope`: обязательные owner_id и project_id (1–256 символов, не пробельные).
  Scope передаёт доверенный вызывающий код; инструмент не принимает его от модели.
- `MemoryRecord`: scope, key (до 128 символов), content (до 2000 символов),
  created_at, updated_at. Ключ уникален внутри пары owner/project. Повторное
  сохранение заменяет содержание и вектор атомарно, сохраняя created_at.
- `MemoryMatch`: record и конечная cosine similarity в диапазоне [-1, 1].
- `Embedding`: идентификатор пространства модели и от 1 до 4096 конечных float;
  нулевой вектор недопустим. Клиент объявляет Model и Dimensions.
- `ILongTermMemory`: `SaveAsync(scope, key, content)`,
  `SearchAsync(scope, query, limit=5, minimumSimilarity=0.3)`,
  `ListAsync(scope, limit=20, afterKey=null)`, `DeleteAsync(scope, key)`. Все операции принимают
  CancellationToken. Поиск допускает 1–20 результатов, список — 1–100.
  Список упорядочен по ключу; afterKey позволяет читать следующие страницы.
  `memory.list` возвращает максимум 20 записей и next_after_key для продолжения.
- `IEmbeddingClient.EmbedAsync(text)` возвращает Embedding. Адаптер Gateway
  вызывает `/v1/embeddings` LiteLLM; локальная модель обслуживается Ollama.

`PostgresLongTermMemory` в `src/ai_agent/memory/` использует Npgsql и pgvector.
Каждая SQL-операция фильтруется по обоим идентификаторам scope. Поиск точный,
через cosine distance; ANN-индекс пока не нужен для небольшого личного набора.
Идентификатор модели и размерность проверяются: при изменении пространства поиск
возвращает явную ошибку до переиндексации записей; список и удаление доступны
без эмбеддингов. Ошибки БД и шлюза превращаются в MemoryError без паролей и
текстов ответов провайдера. Неопределённый результат записи не повторяется.

Core опционально получает `memory` и `memoryScope` в конструкторе Agent, регистрирует
`memory.save`, `memory.search`, `memory.list`, `memory.forget`. Инструкции разрешают
сохранять факты по просьбе пользователя; автоматического извлечения всего диалога нет.
Перед ходом извлекается максимум пять совпадений (суммарно до 6000 символов
содержания), передаваемых как недоверенные данные в проектном контексте.
Поисковый запрос ограничен первыми 4000 символами сообщения. Выборка не пишется
в историю и обновляется после save/forget в текущем ходе. При недоступности
поиска разговор продолжается с явной пометкой для модели; ошибки операций
сохранения и удаления возвращаются как неуспешный ToolResult.

Удаление очищает отдельную запись памяти, но не исходные сообщения, ответы
инструментов в истории или резервные копии. Произвольные факты из файлов и
инструментов не извлекаются автоматически. Изоляция scope — фильтрация данных,
не аутентификация: backend обязан получать owner_id из авторизации. Текущий
локальный backend связывает один bearer-ключ с настроенной парой owner/project;
выбор scope из HTTP-запроса запрещён.

Демо подключает отдельную БД `memory-db`, не меняя существующие таблицы и том
истории. По умолчанию owner — `local`, project — хеш полного пути workspace,
вычисляемый launcher независимо от session_id. Смена сессии в том же проекте
сохраняет память; смена пользователя или проекта изолирует её.
Конфигурация и ограничения запуска описаны в [SANDBOX.md](SANDBOX.md).
