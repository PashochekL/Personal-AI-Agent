# Командная разработка

Сначала полностью прочитайте [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)
и [docs/CONTRACTS.md](docs/CONTRACTS.md). Стек и границы модулей обязательны.

## Ветки

- `main` — стабильная версия, прямые изменения запрещены.
- `develop` — общая интеграционная ветка.
- `feature/...` — работа над компонентом от актуальной `develop`.

Первоначальная основа готовится локально в `develop`; её коммит и публикацию
выполняет владелец репозитория. На этом этапе feature-ветки не создаются.
После публикации основы и согласования открытых контрактов участник с чистым
рабочим деревом выполняет:

```sh
git fetch origin
git switch develop
git pull --ff-only origin develop
git switch -c feature/agent-core
```

Если локальной `develop` ещё нет, вместо `git switch develop`:

```sh
git switch --track -c develop origin/develop
```

Каждый участник выбирает свою ветку:

| Ответственность | Ветка |
| --- | --- |
| Core | `feature/agent-core` |
| Infrastructure | `feature/infrastructure` |
| Memory & Interfaces | `feature/memory-interfaces` |
| Integrations | `feature/integrations` |

Не перезаписывайте существующую ветку. Если pull с `--ff-only` отклонён или есть
незакоммиченные изменения, разберите ситуацию с владельцем, сохранив его работу.
Не применяйте принудительное обновление истории.

## Контракты и интеграция

Работайте преимущественно в своих каталогах. Изменение чужого модуля требует
необходимости и разрешения владельца. `shared/` меняется только после явного
согласования затронутых участников. В предложении укажите причину, точные поля
и сигнатуры, совместимость и необходимые изменения адаптеров и тестов.
Утверждённые контракты и отдельно отложенные вопросы перечислены в CONTRACTS.md.
Не изменяйте утверждённые поля и правила без нового согласования команды.

Используйте типы C# и async/await для согласованных интерфейсов.
Не импортируйте внутренние классы чужих модулей в обход контрактов.
Не создавайте циклические импорты или независимые Agent Loop.
Зависимости добавляйте через NuGet только по необходимости.

## Проверка и Pull Request

1. Установите .NET SDK 10.
2. Добавьте тесты нового поведения и ошибок. Внешние сервисы подменяйте
   тестовыми адаптерами в проверках контрактов.
3. Запустите `dotnet run --project tests/ContractTests/ContractTests.csproj` и `dotnet build src/ai_agent/shared/Shared.csproj`.
   При изменении ядра или памяти также запустите `dotnet run --project tests/CoreTests/CoreTests.csproj`
   и `dotnet run --project tests/MemoryTests/MemoryTests.csproj`.
   HTTP-клиент проверяется командой `dotnet run --project tests/CliTests/CliTests.csproj`.
   Интеграция процесса CLI с backend: `pwsh -NoProfile -File tests/BackendTests/run-integration.ps1`.
   Полный автономный набор в Linux: `docker build -f docker/Dockerfile.tests -t personal-ai-agent-tests .`.
   Проверки памяти с настоящей БД описаны в [SANDBOX.md](docs/SANDBOX.md#долговременная-память).
4. Проверьте `git diff --check` и `git status`: секретов и локальных данных быть не должно.
5. Обновите документацию с учётом фактически доступных возможностей.
6. Откройте PR из своей feature-ветки в `develop`: проблема, изменение,
   результат проверок, затронутые контракты. Получите ревью владельцев компонентов.

Объединять PR можно после прохождения проверок, согласования shared и проверки
совместимости компонентов. Полный сценарий CLI → Core → LLM → tool → история
проверяется по мере появления реализаций. Общая очередь и порядок изменений
истории одной сессии должны быть едиными для интерфейсов. Task Service / Worker
сериализует всё выполнение Agent.run одной сессии; блокировки отдельных записей
истории недостаточно. Первоначальные API, очередь и Worker реализованы;
запуск и проверки описаны в [BACKEND.md](docs/BACKEND.md).
Обычный CLI использует HTTP backend; прямой пример Core сохранён в
`examples/SandboxConsole`. Команды и ограничения описаны в [CLI.md](docs/CLI.md).
Перенос из `develop`
в `main` — через отдельный проверенный PR по решению команды.

## Секреты и работа AI-инструментов

Не добавляйте ключи, пароли, токены, реальные `.env`, дампы и пользовательскую
историю в Git или логи. `.env.example` содержит только пустые значения и безопасные
настройки. Не считайте маскирование значений разрешением логировать настройки.

AI-инструменты соблюдают [AGENTS.md](AGENTS.md). Без явного разрешения владельца
они не выполняют commit, push, merge, rebase, удаление веток, force push,
`reset --hard` и `clean`. Результаты этапа и предлагаемое название коммита
передаются человеку для проверки.
